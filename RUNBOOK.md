# RUNBOOK — эксплуатация сервиса

## 1. Контейнер не запускается

Из корня репозитория выполните:

    docker compose ps
    docker compose logs --tail=100
    docker compose up --build

Ищите ошибки установки зависимостей, импорта Python, порта, отсутствующей конфигурации или модели. Убедитесь, что в репозитории присутствуют models/best.onnx и configs/detect.yaml.

## 2. /health отвечает 200, а /ready — 503

Это ожидаемо во время прогрева: health проверяет живость HTTP-процесса, ready — готовность модели к инференсу.

    curl http://localhost:8000/health
    curl http://localhost:8000/ready
    docker compose logs --tail=150

В поле stage может быть starting, loading_model, warming_up, ready или error. При error проверьте лог model_startup_failed, путь MODEL_PATH и совместимость модели с ONNX Runtime.

## 3. /detect возвращает ошибку

Проверьте формат JPEG/PNG/WebP, размер файла (не более 4 MB), корректность изображения и HTTP-код. 413 означает превышение размера, 415 — неподдерживаемый тип, 503 — модель ещё не готова, 500 — внутренняя ошибка инференса. Найдите request_id в JSON-ответе и логах.

## 4. Растёт задержка

Проверьте latency_ms в HTTP-логах и inference_ms в ответе /detect. Сравните холодный старт, загрузку файла и фактический инференс. На Render Free процесс может засыпать после простоя, а 0.1 CPU ограничивает скорость. Не запускайте несколько параллельных инференсов и не добавляйте PyTorch в production requirements без необходимости.

## 5. Плохие ответы или подозрение на drift

Сохраните анонимизированные примеры для контролируемой проверки в локальном окружении. Сравните условия освещения, ракурс, размытие, фон, долю пропусков и ложных детекций на размеченной выборке. Один неудачный пример не доказывает drift. Не переобучайте модель автоматически на пользовательских загрузках; нужны контролируемая разметка и отдельная оценка качества.

## 6. Найти запрос по request_id

Локально:

    docker compose logs

Поищите UUID из ответа API или заголовка X-Request-ID. В Render Dashboard откройте Web Service → Logs и найдите точный request_id. Тело запроса и изображения в лог не попадают.

## 7. Откат на предыдущий релиз

В Render Dashboard откройте историю Deploys и выполните rollback на предыдущий успешный deploy, если действие доступно для сервиса.

В Git можно вернуть ветку на известный исправный коммит отдельным revert-коммитом:

    git log --oneline -10
    git revert <SHA_исправления>
    git push origin main

Не используйте force push. Если это первый релиз v1.0, сначала выберите предыдущий рабочий deploy или сохранённый коммит — не придумывайте тег, которого нет. После отката проверьте deploy, /health, /ready и smoke-тест.

## 8. Проверка восстановления

    curl -i http://localhost:8000/health
    curl -i http://localhost:8000/ready
    bash scripts/smoke_test.sh

Затем выполните настоящую детекцию на демонстрационном изображении. Успешный health сам по себе не означает, что модель готова.
