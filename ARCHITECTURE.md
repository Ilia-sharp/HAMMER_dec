# Архитектура Nazdratenko Hammer Detector

## Схема

~~~mermaid
flowchart LR
  A[Браузер] --> B[Одностраничный UI]
  B --> C[FastAPI]
  C --> D[Проверка изображения]
  D --> E[ONNX Runtime CPU]
  E --> F[YOLO26n best.onnx]
  F --> G[JSON с рамками и confidence]
  G --> H[Canvas в браузере]
  C --> I[JSON-логи: request_id, latency_ms, model_version]
  J[Docker / Render Blueprint] --> C
~~~

## Жизненный цикл

1. Uvicorn поднимает HTTP-приложение.
2. Фоновый поток загружает ONNX-модель и создаёт CPU session с одним потоком.
3. API выполняет пробный инференс на синтетическом изображении.
4. /health остаётся доступным во время загрузки; /ready возвращает 503, пока модель не прогрета.
5. После успешного прогрева /ready начинает возвращать 200.
6. Каждый запрос получает request_id; в JSON-логи попадают метод, маршрут, статус, latency_ms и model_version без тела запроса.

## Обработка изображения

POST /detect принимает multipart/form-data с полем file. Максимальный размер файла — 4 MB; максимальная сторона изображения — 1280 px. Картинка декодируется в памяти. ONNX Runtime CPU выполняет инференс, затем сервер применяет порог уверенности, NMS и возвращает рамки. Canvas рисует результат в браузере.

## Выбор health check

Render проверяет /health, чтобы прогрев модели не блокировал запуск HTTP-сервиса. Клиент и smoke-тест отдельно проверяют /ready — это подтверждает готовность именно к инференсу.
